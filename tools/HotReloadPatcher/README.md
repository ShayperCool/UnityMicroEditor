# Hot reload patch builder

After a C# edit in a watched session the runner recompiles the changed game assemblies as usual and then runs this executable. It compares each assembly the Player loaded with its new compilation, classifies every difference, and emits one patch assembly per changed assembly: `<name>.HotReload.<generation>.dll` with a portable PDB. The applier in the Player loads the patch and redirects the old methods to the new ones.

It is built with the .NET 8 SDK of the Unity installation and uses only `System.Reflection.Metadata` from the shared framework: no package, no reference, no Unity process.

```bash
dotnet HotReloadPatcher.dll <request.json>                       # one JSON document on stdout, exit 0
dotnet HotReloadPatcher.dll --codes                              # every reason and note code with its meaning
dotnet HotReloadPatcher.dll --explain <request.json> <member id> # what the comparison sees of one method
```

A request that cannot be read (bad JSON, a missing or invalid assembly, an unreadable previous result) is a message on stderr and exit code 1. An edit that cannot be patched is a normal result with the verdict `unsupported`. So is a failure of the tool on one assembly: the reason is `internal_error` with the exception, and nothing is written.

A result with the verdict `unchanged` can still have notes: a changed accessibility of a method and a removed start-up method leave every body as it was, and the Player keeps the loaded form until it restarts. Whether such a difference is a note or a refusal follows one line: an edit of which nothing reaches the Player is refused, and an edit that is applied with something left out is a note. A field that is made `public` or private, or given or relieved of `readonly`, so that Unity starts or stops serializing it is refused (`serialization_changed`): the bodies are as they were, and the one thing the edit is for, a value from a scene, a prefab or an asset, is not read before a restart. `[SerializeField]` on the same field is refused for the same reason, as an attribute change. An accessibility that changes nothing Unity serializes (a static or read-only field, a field that is marked already, a class Unity does not serialize, a method) is the note `accessibility_changed`, and so is one on a field whose type Unity never serializes: a delegate, a dictionary without `[SerializeField]` (Unity 6 serializes a `[SerializeField] Dictionary<K,V>` at the top of a field) or another type of the class library, `object`, an interface or a class without `[Serializable]` (unless the field is a `[SerializeReference]`), a nullable, a tuple, a multi-dimensional array, an array or list of arrays or lists, an enum of 64 bits, and the engine's types it skips (`Coroutine` and the other yield instructions, `Ray`, `RaycastHit`, `Plane`, `RangeInt`, `Touch`, `NativeArray<T>`, `ObjectPool<T>`; an engine type is serialized when it is an engine object, one of the types native code stores in a form of its own such as `Vector3`, `AnimationCurve` or `PropertyName`, or a `[Serializable]` class or struct that is not abstract). A fixed buffer of a `[Serializable]` struct is serialized. These rules were read from Unity 6000.6.3f1 (SerializedObject of components with such fields, the analyzer warnings UAC1001, UAC1011 and UAC1015) and match the layout helper of `tools/LifecycleCompiler`. A field type that cannot be decided (a type parameter, a type of an assembly that cannot be read) counts as serialized. An added serialized field is a note too: the patch gives the field to the code that uses it, and the note says that scenes do not fill it. The runner prints the notes of an `unchanged` result on its `unchanged` or `updated` event.

A note about a method the patch carries has a `revision`: a short hash of what that method runs in this result, or `g<generation>` for a note about what the step from the previous patch changed (`earlier_patch_delegates_keep_old_code`). `added_method_delegate_identity` is a condition that stands from patch to patch and has none, so it is told when it begins and not with every later patch. The revision of `added_method_named_by_string` also covers where the string stands (the types whose code holds it, and how often), so a later edit that starts to call an added method by name brings the note anew. A patch repeats every difference from the loaded assemblies, and with it every note. The same code, member and revision as in the result before means that the note only still stands; anything else is about code that changed since. The runner lists those apart (`newNotes`).

The request and the result are described at the top of `Program.cs`. Two of their members serve patches that follow each other in one Player:

- Each assembly of a result lists its `patchMembers`: the methods that only the patch defines (added methods, lambdas, local functions, closure and state machine methods), each with a hash of the code it can run. Replacements of loaded methods are not listed: callers and delegates name the loaded method, and every patch redirects it anew.
- The request of the next patch names that result as `previousResult`. Nothing redirects from one patch into the next, so a delegate, coroutine or async call that the earlier patch created keeps the earlier code. The builder compares the two and says so (`earlier_patch_delegates_keep_old_code`), and it reports a delegate of an added method that both patches have (`added_method_delegate_identity`): `-=` does not find a handler the earlier patch subscribed. An assembly that was patched before and is byte-identical to the loaded one again must still be listed (with `current` equal to `loaded`) to get these notes.

## How it decides

Two compilations of the same source never agree on metadata tokens, and the compiler renumbers its generated members (`<M>b__5_0`, `<>c__DisplayClass5_0`, `<M>d__5`, `<>f__AnonymousType3`) whenever a member is inserted earlier. So a method is compared by what its tokens mean, and the compiler-generated members it owns are compared by structure (`Canon.cs`). A comment, a reordered member or a new file changes nothing in that form.

Generic code names its own members through an instantiation of their type (`Box<!0>::<Get>b__1_0`, `<>c__2<!!0>::<>9__2_0`). Such a reference is followed to the definition it names, so a lambda or local function of a generic method or of a method of a generic type belongs to that method like any other, and an edit in it is the refused edit of generic code that it is. A reference that names no member of its type fails the comparison of the assembly (`internal_error`).

A body is compared through the method that owns it. As a net under that, the compiler-generated methods that code of the assembly can run and that no user method reaches are compared as a set between the two compilations; a difference there means that an edit lies where the comparison did not look, and it is refused with `unowned_generated_code`. No source known to the tests produces it; the diagnostic request member `fault: "owner"` does.

The compiler also emits the method of a lambda or local function that nothing names: code behind a `return` or a `throw`, a branch that a constant switches off, a local function without a call. Such a method cannot run in either compilation and is left out of the net, so switching a method off for a moment, flipping a debug flag or saving a helper before its first call is the edit of the method around it and no more, and an edit inside such code is no change. What can run is found by following every token of every body from the methods a user wrote (`Reach` in `Diff.cs`); a reference that walk cannot place counts as a use of every generated method of that name, so the net is wider than the comparison it stands under. The net costs nothing unless a generated method is left over after the comparison.

The policy is in `Diff.cs`, and in `Netcode.cs` for assemblies that use Netcode for GameObjects. An edit is patched only when the patch and the runtime are known to carry it exactly; everything else is refused with a code from `Codes.cs`. One refused change makes the whole result `unsupported`, and no file is written.

## Netcode for GameObjects

The compiler runs the package's post-processor on every assembly whose compiled image references `Unity.Netcode.Runtime` (`tools/NetcodePostProcessor`). The builder is given the post-processed images and compares them like any others, so it also sees what the post-processor generated, and it reads from that what Netcode registered when the Player started. The rule: what is registered once, and what the two ends of a connection must agree on, is fixed in a running Player; everything else is code like any other.

| Edit | Result |
| --- | --- |
| A method body of a NetworkBehaviour or of any other class of the assembly, `Update`, an `OnValueChanged` handler, a lambda; an added method or field; a first call of the Netcode API in a body | Patched as in any assembly. |
| `OnNetworkSpawn`, `OnNetworkPreSpawn`, `OnNetworkPostSpawn`, `OnNetworkSessionSynchronized`, `OnInSceneObjectsSpawned` of a NetworkBehaviour, and a method only they call | Patched, with the note `spawned_objects_keep_state`: Netcode ran it for the objects that are spawned and does not run it again; objects spawned after the patch run the new body. |
| `OnIsServerAuthoritative` of a class below `NetworkTransform` (the owner-authoritative `ClientNetworkTransform` of the documentation) | Patched, with the note `spawned_objects_keep_state`: NetworkTransform reads it when an object is spawned and keeps that authority, while later calls take the new answer. |
| A serializer or message handler a `[RuntimeInitializeOnLoadMethod]` registers (`UserNetworkVariableSerialization<T>`, a named message) | Patched, with the note `runtime_initializer_changed`: the registration ran when the Player started and is not made again, so no Player uses the new one before it restarts. |
| The body of an RPC | Patched. The post-processor puts the code that checks the session, writes the parameters and sends them in front of the body; the patch carries the whole post-processed body, as a restarted Player would run it. The handler Netcode registered keeps calling the loaded method, which the Player redirects. The send code must be the same in both images: it is compared up to its first store into `__rpc_exec_stage`, its locals by type and order of first use, since their indices follow those of the body and move with every local the body gains. |
| RPCs, or the classes whose network variables need a serializer, declared in another order | No change: Netcode looks the RPCs of a class up by id, and each serializer belongs to one type. The registrations are compared as sets. |
| An RPC added, removed or renamed; its parameters changed; its attribute changed (also `custom_attributes_changed`); the code that sends or receives it changed (how a parameter is serialized); who may invoke it | `netcode_rpc_changed`. The RPCs of a class are registered by an id of the module and the signature when its first object is initialized. |
| A NetworkVariable or another `NetworkVariableBase` field of a NetworkBehaviour added, removed, renamed, retyped or reordered | `netcode_variable_changed`. Every object lists its network variables once, and both ends replicate them by position. |
| A network variable of a value type that needs a serializer of its own, `[GenerateSerializationForType]` | `netcode_serialization_changed`. Serializers are registered when the Player starts. |
| Anything else in what the post-processor generates: the name of a NetworkBehaviour, a class that becomes one or stops being one, a generated member the builder does not know, an assembly that starts or stops using Netcode with something to register | `netcode_generated_code_changed`. An assembly whose first use of Netcode registers nothing (a call of the API in a method body) is no change: the post-processor writes its start-up types also then, with an empty registration. |
| A new NetworkBehaviour or `INetworkSerializable` type; a field of an `INetworkSerializable` struct; the body of its `NetworkSerialize<T>` | Refused as in any assembly: `type_added`, `struct_layout_changed`, `generic_method`. |
| Any edit, when an image is not in the post-processor's form, or the assembly is the Netcode runtime itself | `netcode_assembly`. |

What the post-processor adds is recognised by its names: `__initializeRpcs`, `__initializeVariables`, `__getTypeName` and `__rpc_handler_<id>` in a class, the types of the namespace `__GEN`. In a class the post-processor took for a NetworkBehaviour (one that declares `__initializeRpcs`), every method whose name starts with two underscores counts as generated (the language reserves such names; `__UnityPlay_` is the lifecycle rewrite's). These members are compared as a set, by what they run; they are never patched. Before anything is compared, both images are checked for the form `Netcode.cs` describes: the start-up registration exists, every class with RPCs or below NetworkBehaviour has its three generated methods and one handler per RPC, and every RPC body starts with its send code. An image that fails the check comes from a version of the package the builder does not know, or was not post-processed: nothing says what was registered, and every edit of it is refused; an identical pair of such images is still no change. The form was read from, and the rules were run in a Player with, `com.unity.netcode.gameobjects` 2.13.2.

The request says nothing about Netcode: an assembly whose image does not reference the Netcode runtime was not rewritten, whatever the project's assembly graph allows it to reference.

Limits of these rules:

- They cover what Netcode generates and registers. What the game itself agrees on with its peers in ordinary code (the body of a custom `FastBufferWriter` extension, a named message, the meaning of a value) is patched like any code.
- A patch reaches one Player. Another peer takes the same edit from its own session; until then the two run different bodies, which is safe for the edits that are patched, because nothing of them is on the wire.
- The initial value and the permissions given to a `NetworkVariable` constructor are code of the class's constructor: patched with `constructor_applies_to_new_objects`, so the objects that exist keep what they were made with.
- A version of the package that registers something at start-up through other members than those above is not recognised as one; the form check finds the versions that lack these members or this send code.
- In a NetworkBehaviour a method that the game names with two leading underscores is taken for generated code, and every edit of it is refused.

What a patch contains (`Emit.cs`):

- An instance method of a class becomes a static method with the receiver as first parameter. An instance method of a struct stays an instance method, on an empty stand-in struct: that keeps the calling convention of a struct receiver with a hidden return buffer.
- Bodies are copied byte for byte with their tokens rewritten in place. A call to a changed method keeps naming the loaded original, which the Player redirects; a call to an added method names the copy in the patch.
- Closure classes and iterator/async state machines are copied as new top-level types; the shared `<>c` class and `<PrivateImplementationDetails>` are copied in part.
- An anonymous type or a generic compiler-generated type is never copied. The patch refers to the loaded type of the same structure, or the edit is refused.
- A field the loaded type lacks is reached through accessors that call `UnityMicroEditor.HotReload.FieldStore`, with the id `<assembly>|<type>|<field>`.
- An added instance method starts with a check of its receiver, because its copy is static and called with `call`: a null receiver throws at the call, as `callvirt` does.
- A removed `void` Unity message is redirected to an empty method, unless the engine works differently while the message exists.
- An edited lambda or local function is redirected from its old method when the pairing is proven: the code that creates it is identical in both compilations apart from the names of the generated members, so the k-th lambda of one is the k-th lambda of the other. An async lambda or an iterator local function is a stub that starts a state machine; the stub is redirected when the state machine changed. In every other case the result carries `lambda_not_remapped`, except when the old lambda is unchanged at the same position among the lambdas of its method.
- A compiler-named method that is virtual (the `<Clone>$` of a record) is never copied: the patch calls the loaded one, virtually.
- The assembly carries the `SkipVerification` permission set and `[module: UnverifiableCode]`. Its types live in the namespace `HotReload.G<generation>`.

Every emitted patch is read back and verified before it is published (`Verify.cs`): no type name of a loaded assembly, every reference into a game assembly resolves in the loaded one, the permission set is present, every body decodes, every redirect pair has the same shape.

## Limits

- Generic methods, methods of generic types, added or removed types, virtual methods, constructors and Unity messages, changed static constructors, attribute changes, an accessibility or `readonly` that changes what Unity serializes, `readonly` removed from a static field, changed marshalling of an extern method or delegate, calls with a variable argument list, and what Netcode registers at start-up (see above) are refused; `--codes` lists every reason. Whether an assembly is one of Netcode is read from the two images alone: the post-processor returns an image without that reference as it was.
- Attributes that only a compiler reads are not compared: nullable annotations, the names of tuple elements, `nint`, `dynamic`, `readonly` on a struct or its members, `params`. The attribute types the compiler embeds for them come and go with their first and last use and are neither an added nor a removed type.
- A changed method that the engine calls once for the objects that exist is patched with the note `started_objects_keep_state`: it does not run again for them. These are the parameterless `Start` of a MonoBehaviour, `Awake` of a MonoBehaviour or ScriptableObject, `OnEnable` of a MonoBehaviour (it runs again only when the object is disabled and enabled; what the old body subscribed stays, and a changed `OnDisable` does not undo it), `OnEnable` of a ScriptableObject (when the asset loads) and `OnAfterDeserialize` of an `ISerializationCallbackReceiver`. The lifecycle rewrite moves the bodies of `Awake`, `OnEnable`, `OnDisable` and `OnDestroy` into `__UnityPlay_<message>`; notes name the message the user wrote (`Enemy::Awake()`). A `Start` or `Awake` with parameters and the `Start` of another class are methods of the game and get no note. A class whose base chain cannot be read counts as a MonoBehaviour. A changed spawn callback of a NetworkBehaviour, and `OnIsServerAuthoritative` of a class below `NetworkTransform` (read when an object is spawned and kept), have the note `spawned_objects_keep_state` for the same reason. A changed `[RuntimeInitializeOnLoadMethod]` method, or one that a start-up bridge of the lifecycle rewrite calls, has the note `runtime_initializer_changed`: it ran when the Player started and does not run again, so its new body is not in effect before the next start (a changed static constructor is refused instead: the runtime runs it, not a call the patch could redirect). These notes are also given when only a lambda that the method creates changed, also when that lambda is redirected.
- A changed method that only such methods call gets the note of the method that calls it, naming it (`Enemy::OnSetup()` is called only from `Actor::Awake()`): every caller in the assembly is such a method or another one of these, through calls and virtual calls of the assembly's own methods. A public method, a method a delegate or `ldtoken` takes, a method whose name a string of the assembly holds, an override of a method declared outside the assembly and a Unity message can be called from where the assembly does not show, and get no such note.
- A removed or renamed iterator or async method has the note `running_coroutines_keep_old_code`: the coroutines of it that run keep the removed code, which a restart would not have.
- An added instance method of an engine object has the note `added_method_invisible_by_name`. When a string of the assembly equals the name of an added method the note is `added_method_named_by_string` instead and names the types whose code holds the string: `Invoke("Blast", 1f)` finds nothing in the loaded class and does nothing. The string is compared with the name only; a log text that happens to equal a method name gives the same note. A removed or renamed field gets no note of its own: the loaded storage keeps its value, no new code reads it, and the field that replaces it has the note of an added field. An added instance field has the note `existing_instances_keep_default` when a constructor or an initializer sets it, which the objects that exist never ran, or when a field of the same type was removed by the same edit (a rename does not carry the value over). An added field with neither has its default in every object, old or new, and gets no note.
- The attributes the compiler writes on an iterator or async method (`*StateMachine`, `DebuggerStepThrough`) are not compared, so a method can become one or stop being one. Reflection keeps seeing the loaded attributes.
- Patch code is not redirected to later patch code. What an earlier patch created keeps running that patch; the result of the next patch names it when it is given `previousResult`.
- A removed method that is not a Unity message stays loaded. Code that reaches it by name (`Invoke`, `SendMessage`, a UnityEvent, an animation event) keeps running it until a restart, and so does a coroutine of it that runs (see above).
- A type reference scoped to the module itself means the module's own type. The compiler never writes one; the Netcode post-processor does, for a struct of the game that an RPC sends.
- A class counts as an engine object unless its base chain is read to `System.Object`. Bases in assemblies outside the request are read from the directory of the loaded assembly; when that fails, a method named like a Unity message is treated as one.
